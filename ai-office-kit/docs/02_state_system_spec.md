# 02. 状態システム仕様（office_state.json）

チャットやスクリプトから「誰が今なにをしているか」をオフィス画面に反映する仕組み。
HTMLと**同じフォルダ**に置いた `office_state.json` を、画面が定期的に読み込む。

## 読み込み
- 取得先: `office_state.json`（クエリ `?state_url=...` で差し替え可）。
- ポーリング: **30秒ごと**（`setInterval(pollState,30000)`）。初回は即時。
- 取得は `cache:"no-store"`。エラー時は握りつぶして前回状態を維持。

## スキーマ
```jsonc
{
  "overrides": [
    {
      "name": "（TEAMのnameと完全一致）",  // ← 主キー。一致しないと無視される
      "status": "working",                 // "working"（作業中） or "done"（完了）
      "task": "いま何をしているかの一文",
      "at": "2026-07-16T15:05:00+09:00",   // ISO時刻。全ライフサイクルの基準時刻（必須推奨）
      "until": "2026-07-16T15:40:00+09:00" // 任意。この時刻を過ぎたら無効化（working向け）
    }
  ],
  "log": [
    "15:05 ジョン: 〇〇を提出。次は△△",     // 業務日誌。直近4行だけ表示される
    "..."
  ]
}
```

## 反映ルール（重要）
1. `name` は `TEAM[].name` と**完全一致**が必須。全角/半角・記号・スペースまで一致させる。
2. `until` があり、その時刻を過ぎていると**そのエントリは無効**（表示されない）。
3. `at` があり `status:"done"` で、**現在時刻 − at > 1時間** なら「完了✓」表示は消える（席で待機に移行）。
4. `status:"working"` は、そのキャラを即「作業中（live）」にして席に座らせる（タブ非表示でも反映）。
5. `log` は配列の**末尾4件**だけが画面に出る。1行 = 業務日誌の1エントリ。

## 状態の意味
| status | 画面での見え方 |
|---|---|
| `working` | 席で作業中（メモ＋ペンの頭上アイコン、作業吹き出し） |
| `done`（1h以内） | 「完了✓」表示 |
| （記録なし or done 1h超） | 席で待機（スタンバイ） |
| （12h以上記録なし） | 休憩室で休息（→ `03`） |

## 推奨ワークフロー（1タスクのライフサイクル）
チャットで作業するたびに、次の3段で書き換えると自然に見える。
1. **開始時**: 担当を `working` ＋ 具体タスク名 ＋ `at`（現在時刻）＋ `until`（+10〜30分）。
2. **完了時**: 担当を `done` にし、`at` を完了時刻へ。必要なら統括役を次に `working`（最終チェック）に。
3. **提出時**: 統括役を `done`（提出済み）にし、`log` に1行追記。
> `done` のエントリは**消さず12時間は残す**と、待機→休息のライフサイクル（`03`）が正しく働く。

## 担当マッピングの考え方（受け取り側が定義する）
「どの作業をどのメンバーに割り当てるか」は各自のチーム次第。
おすすめは、作業カテゴリ→メンバー名の対応表を1枚持っておき、開始時にそのメンバーを `working` にすること。
（例：デザイン=デザイナー、実装=エンジニア、調査=リサーチ担当、最終確認=統括…といった対応表）

## よくある詰まり
- **反映されない** → まず `name` の完全一致を疑う。次に `until` が過去でないか、`at` が未来すぎないか。
- **表示がすぐ消える** → `done` の `at` が1時間以上前。想定通り（完了✓は1hで消える仕様）。
- **JSONが読めない** → `file://` で開いている。ローカルサーバー経由にする（→ `05`）。
