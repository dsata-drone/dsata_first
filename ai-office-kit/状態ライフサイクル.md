# オフィス状態ライフサイクル仕様

エージェントの状態がいつ・どう変わるかの正式な定義。
実装: フロントは `ai_office_1.html`（updateWorker / stateLabel / pollState）、
バックエンドは `automation/orchestrator.py`（rule_based_decide / compute_waiting）。

## 状態一覧と表示

| 状態欄の表示 | 内部状態 | 場所 | 意味 |
|---|---|---|---|
| 作業中 | live | 自部署のデスク | 実稼働を検知している間だけ |
| 完了✓(1h以内) | desk | 自部署のデスク | 完了報告から1時間は成果を掲示 |
| 待機中(〇〇待ち) | desk / rest | 休憩室（移動前は席） | 次の一歩の条件が判明している待機 |
| 待機中(休憩室) | rest | 休憩室 | 条件未算出の待機（次サイクルで理由が付く） |
| 休息中(稼働なし12h+) | rest | 休憩室 | 12時間以上稼働がない深い待機 |
| 休憩室へ移動中 / 席へ戻り中 | toBreak / toDesk | 通路 | 歩行アニメーション |

## 「作業中」になる条件（トリガー）

次の**いずれか**を満たした瞬間に live になる:

1. **采配**: orchestrator の毎時サイクル（Claude采配またはルールベース）が
   `office_state.json` の overrides に `status:"working"` を書く。
   `until`（1〜4時間）を過ぎると自動で解除され待機に戻る。
2. **社長指示**: オフィス画面の指示バー → `/api/command` 経由で同じ overrides が書かれる。
3. **実稼働検知**: activityブリッジ（office_bridge.py）がセッションログの更新を検知
   （検知から90秒間 live 扱い）。

## 待機 → 休憩室への移動

- 完了✓の掲示（1時間）が終わり、かつ最後の稼働から **60秒**（`IDLE_TO_BREAK_MS`）
  経過すると、デスクを離れて**マップ右上の休憩室**へ歩いて移動する。
- 休憩室の座席（`SPOTS`・10枠）が満席の間は席で待ち、15秒ごとに再試行する。
- 稼働なしが12時間（`STALE_MS`）を超えると表示が「休息中」に変わる（場所は同じ）。

## 休憩室 → デスクへの復帰

作業が割り当てられて live 条件を満たした瞬間（または新しい完了報告が付いた瞬間）、
休憩室の座席を解放して自部署のデスクへ歩いて戻り、「作業中」になる。

## 常時稼働 — 待機・カウントダウン停止の完全撤廃

「指示待ち」「条件待ち」「〇時間カウントダウン」による長時間停止は存在しない。
`IDLE_LIMIT_MIN=0`（待機許容ゼロ）により、**毎サイクル・手空きの全員に必ず仕事が入る**。

- 采配・バトンパスの後、残った手空きメンバー全員へ `ensure_min_activity` が
  その場で**常時稼働タスク**を自動生成して4時間の「作業中」にする。
  選定の優先順（`pick_activity_task`）:
  1. **ロール別バックログ**（`AIチーム_ナレッジ/ロール別バックログ.md`・ローテーション）
     — 役割に応じた定常業務・自主研究（例: ゲン→9月に向けたLTV計測モデルの事前調査）
  2. **先行準備の自動創出** — P4-P5の将来タスクから「【先行準備】〇〇に向けた事前調査・
     準備ドキュメントの作成」を生成
  3. 共通バックログ（`_default`）→ ④汎用の自主研究タスク
- 通常采配（P0〜P3）が先に走るため、実タスクがある人はそちらが常に優先される
- 依存タスク待ち（〇〇のタスク完了待ち）の間も同じルールが適用され、
  待ちながら定常業務で稼働する
- **フロントエンドの自主タスク**: サイクル間のわずかな隙間も止まらない。タスクが
  途切れたエージェントは15秒でリフレッシュ（休憩室・90〜180秒）に出た後、
  リサーチ・改善・ドキュメント整理などの**自主タスクを自己生成**してデスクへ戻り
  「作業中(自主タスク)」になる（次の采配が届いた瞬間に本物のタスクへ差し替え）。
  休憩室は「数分のリフレッシュ専用」の場所になった

## 待機理由「〇〇待ち」の算出（orchestrator.compute_waiting）

毎サイクル、working でない全メンバーについて次の優先順で理由を決め、
`office_state.json` の `waiting`（`{名前: 理由}`）に書き出す。画面は30秒ポーリングで反映。

1. **依存タスク未完了** — 采配盤の自分のタスクに `依存:名前` が付いていて、
   その名前の担当に未完了のP0〜P3タスクが残っている → 「〇〇のタスク完了待ち」
2. **実行中タスクあり** — P0〜P3に自分の未完了タスクがある（次サイクルで采配される）
   → 「ジンの再采配待ち」
3. **時期・条件付きタスク（P4-P5）** — タスク文から条件を抽出:
   「補助金」→ 補助金採択待ち / 「9月」→ 9月本番待ち / 「毎朝」→ 毎朝7時の定期作業待ち /
   「毎週土曜・週次」→ 週次実行日(土曜)待ち / その他 → 時期・条件待ち
4. **タスクなし** → 「社長指示待ち」

どの理由にも、稼働保証までの残り時間「・あと〇〇で自動稼働」が併記される
（例:「待機中(9月本番待ち・あと2時間で自動稼働)」）。待ちっぱなしの表示は存在しない。

## エージェント間の自律連携（コラボレーション）

エージェント同士が人間の指示なしで仕事を依頼・受け渡しする。
データモデルは `office_state.json` の `collaborations`:

```json
{"from_agent":"セオ","to_agent":"フミ","request_type":"handoff|help",
 "status":"pending|active|completed","message":"…をお願いします！",
 "task":"比較記事の初稿執筆","timestamp":"…","until":"…"}
```

- **進捗の自動加算**（bump_progress）: 作業ブロック（采配1回）の満了ごとに
  采配盤の該当タスクへ **+25%**。100%到達＝完了が連携の引き金になる
- **バトンパス**（process_handoffs）: `依存:名前` の上流タスクがすべて100%になった瞬間、
  下流メンバーへ自動でタスクを引き渡し「作業中(〇〇からの依頼)」で起動
- **応援要請**（process_help_requests）: `応援:名前` 付きタスクを担当者が作業中のとき、
  応援者が手空きなら「【応援】〇〇を支援」サブタスクを自動発行（help連携）
- 連携レコードは until 経過で completed になり、6時間後に自動削除（最大12件）

### 見える化（フロントエンド）
- 連携中の2人の間に**点線コネクションライン**（handoff=琥珀色／help=シアン、流れる破線）
- 依頼送信時、送信元→送信先へ**光のパケットが飛ぶアニメーション**
- 送信元「💬 〇〇さんに依頼を送りました！」／着弾時に受信側
  「💬 〇〇さんから依頼受信、開始します！」の対話吹き出し（約3秒）
- 状態欄は「**作業中(〇〇からの依頼)**」表示
- テスト用: `ai_office_1.html?demo=collab` で黄金コンビ（セオ→フミ／ルナ→ニジ）の
  モック連携を12秒周期で再生。バックエンド検証は `automation/demo_collab.py`

## 采配盤の依存タスク記法

`JOHN_TASKBOARD.md` の行に `依存:名前` を付ける:

```
- (フミ)：比較記事の初稿執筆(セオの構成案を受けて) 依存:セオ 進捗:5%
```

依存先（セオ）のP0〜P3タスクがすべて100%になるまで、フミには采配されず
状態欄に「待機中(セオのタスク完了待ち)」と表示される。完了した次のサイクルで自動采配される。
（ルールベース采配・Claude采配の両方がこの記法に従う）
